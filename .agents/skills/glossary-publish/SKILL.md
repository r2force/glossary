Исходники находятся в `site/`; Jekyll собирает их в `_site/`. Используй команды и окружение из [README](../../../README.md); полная проверка — `PYTHON=.venv/bin/python scripts/check.sh`. Для повторной сборки не перезаписывай исходники коллекций.

Для локального запуска нужны Ruby 3.3 и Bundler версии из `site/Gemfile.lock`. `scripts/check.sh` сам подключает `.tools/env.sh`, если файл существует; для отдельных команд подключи его вручную. CI готовит собственное окружение. Машинные зависимости не коммить и не привязывай рабочие команды к `/tmp/`.

Проверь реальные изображения Git LFS, соответствие готового HTML содержимому `site/`, ссылки и якоря, метаданные, sitemap и повторяемость сборки. Учитывай `url` и `baseurl` из `site/_config.yml`. Для локальных ссылок нужен `relative_url`, для canonical и sitemap — `absolute_url`.

При изменениях оформления сверяй результат с предпочтениями в [AGENTS.md](../../../AGENTS.md), просматривай затронутые страницы на широком и мобильном экранах. Для переходов между статьями проверь оба направления, первый и последний материал буквы, а также раздел с единственной статьёй; пустых или ведущих на себя карточек быть не должно. Эффекты, от которых пользователь отказался, не включай в незавершённые задачи.

Публикуй только когда отправка изменений или публикация входят в задачу пользователя. Workflow `.github/workflows/deploy-pages.yml` собирает, проверяет и загружает `_site/` официальным механизмом GitHub Pages. До изменений настроек Pages проверь текущий источник и пользовательский домен; сохраняй действующий домен в пределах поручения.

После публикации проверь главную, буквенные разделы начала, середины и конца, отдельные выставки, оригиналы и миниатюры изображений, а также неизвестный URL с ответом 404. В результате укажи запуск, адрес сайта и наблюдавшиеся проверки. Разделяй локальную проверку и проверку живой публикации.
