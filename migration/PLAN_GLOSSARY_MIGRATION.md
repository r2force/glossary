# План переноса glossary.ufacsdb.ru на статический сайт GitHub Pages

## 1. Цель и исходные условия

Необходимо полностью перенести информационное содержимое сайта **https://glossary.ufacsdb.ru/** (Joomla 1.5) в статический сайт, размещённый в текущем GitHub-репозитории и публикуемый через GitHub Pages.

**Каталог результата:** `site/` в корне репозитория.

Ключевая задача — перенести тексты всех материалов, в первую очередь описания книжных выставок, и прикрепить к ним соответствующие изображения, которые пользователь уже добавил в репозиторий.

Переносить нужно именно содержимое:
- тексты введения, заключения и всех описаний выставок;
- заголовки и подзаголовки;
- абзацы, списки, таблицы и другие значимые элементы структуры;
- изображения, подписи и их расположение относительно текста;
- содержательные ссылки внутри материалов.

### Что не нужно переносить

Не переносить дизайн и пользовательский интерфейс старого сайта:
- Joomla-шаблон, CSS и JS старого сайта;
- верхнюю и боковую панели, меню и навигационные модули Joomla;
- кнопки печати, счётчики, виджеты и прочие служебные элементы;
- оформление старых страниц как таковое.

Не нужно воспроизводить внешний вид исходного сайта. Достаточно корректного, семантического HTML с минимальным оформлением, необходимым для чтения.

**Главный приоритет — полнота и точность переноса, а не дизайн.** Не заменять оригинальные тексты пересказами и не редактировать авторский стиль.

## 2. Разрешённые инструменты и автоматизация

Для выполнения переноса **можно и нужно использовать любые доступные агенту автоматизированные средства**. Не требуется вручную открывать и копировать каждую статью, если задачу можно надёжно решить программно.

Допускается использовать, в частности:
- терминальные команды и утилиты: `curl`, `wget`, `grep`, `find`, `file`, `identify`, `exiftool`, `git` и другие доступные инструменты;
- Python: `requests`, `httpx`, `BeautifulSoup`, `lxml`, `html5lib`, `urllib`, `Pillow` и собственные скрипты;
- JavaScript/Node.js: скрипты для обхода страниц, разбора HTML и проверки ссылок;
- браузерную автоматизацию: Playwright, Selenium или аналогичные инструменты;
- GitHub CLI (`gh`), GitHub API и доступные инструменты интеграции с GitHub;
- инструменты просмотра изображений, создания контактных листов, сравнения файлов и вычисления хешей;
- любые другие доступные агенту инструменты, если они помогают получить более точный и полный результат.

### Предлагаемый подход к автоматизации

1. Сначала определить структуру Joomla-сайта: найти страницы разделов, ссылки на материалы и варианты URL.
2. Написать скрипт обхода внутренних страниц исходного сайта. Скрипт должен собирать URL, заголовки, содержимое статей, ссылки на изображения и метаданные.
3. Сохранять результаты обхода в промежуточный машиночитаемый реестр (например, JSON), чтобы их можно было повторно обработать без нового обхода сайта.
4. Выделять содержательную область страницы, исключая меню, шапку, подвал, модули и прочие элементы Joomla. Не удалять элементы статьи только потому, что они имеют нестандартную HTML-разметку.
5. Для сложных или некорректно отображаемых страниц использовать браузерную автоматизацию либо получать исходный HTML и разбирать его отдельно.
6. Автоматически сопоставить изображения исходных материалов с уже имеющимися файлами репозитория по именам, исходным URL, размерам, расширениям и другим признакам. При необходимости сформировать контактные листы и проверить изображения визуально.
7. Сгенерировать HTML-страницы и отчёты скриптами, а затем автоматически проверить ссылки, наличие файлов и полноту набора материалов.

### Правила безопасной и надёжной автоматизации

- Не копировать вручную сотни страниц, если можно организовать контролируемый автоматический сбор.
- Не считать результат скрипта правильным только потому, что он завершился без ошибки. Проверять извлечённые тексты, заголовки и изображения на реальных примерах.
- Не выполнять чрезмерно частые запросы к исходному сайту: использовать разумные задержки, повторно применять сохранённые результаты и не создавать лишнюю нагрузку.
- Не пытаться обходить авторизацию, CAPTCHA или технические ограничения доступа. Если для доступа необходимы учётные данные или экспорт базы Joomla, запросить их у пользователя, а пока продолжать работу с доступными материалами.
- Если доступен экспорт Joomla или дамп базы данных, его можно использовать как дополнительный источник данных, но результат всё равно сверять с опубликованными страницами и изображениями.
- Сохранять промежуточные данные и логи так, чтобы при сбое можно было продолжить работу, а не начинать полный обход заново.
- Все временные файлы, скрипты и отчёты размещать в подходящих рабочих каталогах. Публикуемые файлы сайта должны находиться в `site/`.
- Не включать в публикацию пароли, токены, cookies, дампы с персональными данными или другие секреты.

## 3. Этап 1. Полная инвентаризация исходного сайта

Перед переносом изучить весь исходный сайт, а не только главную страницу.

Главная страница содержит введение, алфавитный указатель от А до Я и заключение. Необходимо обойти все разделы, вложенные страницы и материалы, на которые ведут ссылки указателя.

Для каждой страницы определить и записать:
1. Заголовок.
2. Исходный URL и, если возможно, канонический URL материала.
3. Тип материала: введение, выставка, заключение, раздел или иной материал.
4. Полный текст и структуру содержимого.
5. Ссылки на изображения в порядке их появления.
6. Подписи к изображениям.
7. Содержательные внутренние и внешние ссылки.
8. Признаки пагинации или продолжения материала на других URL.

Учитывать особенности Joomla 1.5:
- ссылки `index.php?option=com_content...`;
- SEF URL и их варианты;
- дополнительные параметры URL;
- ссылки на материалы из разных разделов;
- пагинацию и материалы, разбитые на несколько страниц;
- повторяющиеся ссылки на один материал.

Не считать статью обработанной только потому, что она найдена в алфавитном указателе. Нужно получить и проверить её полное содержимое.

### Реестр материалов

Создать машиночитаемый реестр, например `migration/source_manifest.json`, а также удобный для проверки CSV или Markdown-отчёт. Рабочие отчёты можно хранить вне `site/`, если они не должны публиковаться.

Пример полей реестра:

| Поле | Назначение |
|---|---|
| `source_url` | Исходный адрес страницы |
| `source_id` | ID материала Joomla, если удалось определить |
| `title` | Заголовок материала |
| `type` | Тип материала |
| `section` | Буква или раздел указателя |
| `content_status` | Статус извлечения и проверки текста |
| `source_images` | Исходные URL изображений в порядке появления |
| `local_images` | Сопоставленные локальные файлы |
| `target_path` | Путь HTML-страницы в новом сайте |
| `notes` | Проблемы и замечания |

В отчёте предусмотреть статусы: найдено, извлечено, проверено, перенесено, требует проверки, ошибка.

Количество материалов в реестре должно соответствовать фактическому количеству найденных материалов. Если точное количество определить не удалось, прямо указать это в отчёте и описать способ подсчёта.

## 4. Этап 2. Инвентаризация и сопоставление изображений

Все необходимые изображения пользователь уже положил в текущий репозиторий.

**Не скачивать изображения повторно с исходного сайта и не заменять их изображениями из интернета.** Источником локальных изображений должны быть существующие файлы репозитория.

### Порядок работы

1. Просканировать репозиторий на наличие изображений.
2. Составить список файлов: путь, имя, расширение, размер файла, размеры изображения и, при необходимости, хеш.
3. Сопоставить изображения с исходными статьями.
4. Использовать для сопоставления исходные URL, имена файлов, HTML-разметку, размеры, визуальное сходство и другие доступные признаки.
5. При большом количестве файлов автоматически сформировать контактные листы для визуальной проверки.
6. Проверить порядок изображений в каждой статье.
7. Проверить подписи и расположение иллюстраций относительно текста.

Не полагаться только на совпадение имён файлов. Не использовать предположительное сопоставление, если оно может привести к публикации чужой иллюстрации.

Если изображение не найдено или сопоставление неоднозначно:
- не подставлять похожую картинку;
- записать проблему в отдельный отчёт;
- указать исходную статью и исходный URL изображения;
- по возможности перечислить кандидатов из локальных файлов;
- продолжить перенос остальных материалов.

### Размещение

Все изображения, которые используются на опубликованном сайте, должны физически находиться внутри `site/`.

Рекомендуемый каталог: `site/assets/images/`.

Если файлы уже лежат внутри `site/`, использовать их на месте. Если они расположены в других каталогах репозитория, скопировать необходимые файлы в `site/assets/images/`, сохранив оригиналы в первоначальных местах.

Не удалять и не перемещать пользовательские оригиналы без необходимости.

Все ссылки на изображения должны быть относительными и корректно работать на GitHub Pages, включая публикацию сайта в подпапке репозитория.

Учитывать регистр символов в именах файлов: `Image.JPG` и `image.jpg` — разные файлы.

## 5. Этап 3. Архитектура HTML-материалов

**Каждое описание книжной выставки должно быть отдельным самостоятельным HTML-материалом и иметь собственный URL.** При этом несколько выставок должны иметь возможность отображаться на одной пользовательской странице — например, на странице алфавитного раздела.

Это два разных уровня:
- самостоятельная страница выставки — полный текст и все изображения;
- страница раздела/подборки — список выставок или краткие фрагменты с переходами на отдельные материалы.

Не объединять сами исходные материалы в один файл вместо отдельных страниц.

### Предлагаемая структура

```text
site/
├── index.html
├── exhibitions/
│   ├── exhibition-1/
│   │   └── index.html
│   ├── exhibition-2/
│   │   └── index.html
│   └── ...
├── sections/
│   ├── a/
│   │   └── index.html
│   ├── b/
│   │   └── index.html
│   ├── v/
│   │   └── index.html
│   └── ...
├── assets/
│   └── images/
├── sitemap.xml
├── robots.txt
├── 404.html
└── .nojekyll
```

Структуру можно адаптировать, но все обязательные свойства должны сохраниться.

### Страницы отдельных выставок

Каждая выставка должна иметь:
- стабильный читаемый URL;
- уникальный заголовок;
- полный исходный текст;
- все соответствующие изображения;
- подписи к изображениям;
- исходный порядок элементов;
- содержательные ссылки, если они есть в оригинале.

Например: `/exhibitions/exhibition-1/`.

Имена URL выбирать последовательно и предсказуемо. Не допускать коллизий при одинаковых или похожих названиях. Желательно зафиксировать соответствие исходного URL новому URL в реестре.

### Объединённые страницы разделов

Создать страницы алфавитных разделов А–Я либо только тех разделов, которые действительно представлены на исходном сайте.

На странице раздела разместить список соответствующих выставок. Для каждой записи можно показывать:
- название;
- короткий фрагмент оригинального текста;
- миниатюру, если она уместна;
- ссылку на полное описание.

Если исходный сайт размещает несколько описаний непосредственно на одной странице, сохранить такую возможность. Однако полные материалы должны оставаться доступны по отдельным URL.

### Подготовка к расширению

Архитектура должна позволять без изменения механизма генерации:
- добавлять новые выставки;
- менять порядок материалов;
- объединять несколько выставок в один раздел;
- создавать тематические подборки;
- изменять способ группировки материалов.

Содержимое каждой выставки хранить независимо от страниц, на которых оно отображается. Можно использовать отдельные HTML-фрагменты, Markdown-файлы или JSON/YAML-описания с шаблонами генерации — выбрать самый простой надёжный вариант.

Если используется генератор, результат его работы должен быть полностью статическим. Не загружать тексты статей через JavaScript `fetch()` при открытии сайта: поисковые системы и пользователи должны получать полный текст непосредственно в HTML.

Не создавать отдельные HTML-файлы, которые существуют только формально, но не доступны по ссылкам и не включены в навигацию/карту сайта.

## 6. Этап 4. Точность переноса содержимого

Тексты переносить максимально точно, без редакторской переработки.

Запрещается:
- сокращать статьи или пересказывать их содержание;
- объединять разные выставки;
- удалять повторяющиеся абзацы;
- менять названия и порядок абзацев;
- исправлять авторский стиль по собственному усмотрению;
- удалять содержательные подписи и ссылки;
- менять смысл текста.

Нужно сохранить:
- оригинальные заголовки и подзаголовки;
- абзацы;
- маркированные и нумерованные списки;
- таблицы и другие значимые структуры;
- смысловое выделение текста;
- ссылки;
- порядок изображений;
- расположение изображений внутри текста;
- подписи к изображениям.

Если исходный материал содержит нестандартную HTML-разметку, проверить её назначение перед очисткой. Не удалять полезное содержимое вместе с элементами старого шаблона.

Все страницы должны быть в UTF-8. Использовать корректную семантическую структуру HTML5:
- `<!DOCTYPE html>`;
- `<html lang="ru">`;
- `<meta charset="UTF-8">`;
- `<title>`;
- `<meta name="description">`;
- основной заголовок `<h1>`;
- корректную иерархию `<h2>`, `<h3>` и других заголовков;
- семантические элементы для списков, таблиц, изображений и подписей.

Не превращать текст статей в изображения или canvas: всё текстовое содержимое должно оставаться доступным как обычный текст HTML.

## 7. Этап 5. SEO и индексирование

Отдельные URL выставок нужны, чтобы поисковые системы могли находить и индексировать каждый самостоятельный материал. Само наличие отдельного файла не гарантирует индексацию: он должен быть доступен по HTTP(S), содержать полноценный HTML и иметь внутренние ссылки.

### Для каждой выставки

1. Собственный постоянный URL.
2. Уникальный `<title>`.
3. Уникальный `meta description`, сформированный по содержанию статьи без выдуманных фактов.
4. Один основной `<h1>`.
5. Абсолютный canonical URL опубликованной страницы.
6. Осмысленные `alt` для содержательных изображений. Не заполнять `alt` набором ключевых слов.
7. Внутренние ссылки из разделов и других подходящих страниц.
8. Включение в `sitemap.xml`.

### Страницы разделов и дублирование контента

Предпочтительный вариант: полный текст индексируется на отдельной странице выставки, а на алфавитной странице размещаются названия и краткие фрагменты с переходами на полные материалы.

Если на странице раздела отображаются полные тексты нескольких выставок, оценить риск дублирования контента и выбрать последовательную стратегию. Не создавать множество почти одинаковых страниц без самостоятельной ценности.

### Для сайта в целом

Создать:
- `sitemap.xml` со всеми индексируемыми страницами;
- `robots.txt` с корректным адресом sitemap;
- `404.html`;
- корректные canonical URL;
- понятные внутренние ссылки.

Не закрывать страницы выставок от индексации. Проверить, что в HTML и метаданных не осталось случайных ссылок на старый Joomla-сайт, кроме тех, которые являются намеренными внешними ссылками из исходных материалов.

При публикации в подпапке репозитория учитывать базовый путь GitHub Pages. Не использовать некорректные абсолютные пути вида `/assets/...`, если они ломают загрузку ресурсов на project site. Предпочитать относительные пути либо корректно вычисляемый базовый URL.

## 8. Этап 6. Технологическая реализация

Использовать максимально простую технологию:
- обычный HTML5;
- локальные изображения;
- при необходимости — небольшой скрипт генерации статических страниц;
- минимальное количество сторонних зависимостей.

Не подключать React, Vue, Angular и другие frontend-фреймворки без объективной необходимости. Для этой задачи они не требуются.

Если используется генератор, он должен:
1. Читать независимые материалы выставок и структуру разделов.
2. Создавать отдельную HTML-страницу каждой выставки.
3. Создавать объединённые страницы разделов.
4. Подставлять корректные ссылки на локальные изображения.
5. Формировать `sitemap.xml`.
6. Проверять наличие используемых изображений.
7. Завершаться с понятной ошибкой, если обнаружены отсутствующие обязательные данные.
8. Быть повторяемым: повторный запуск не должен случайно менять содержимое или удалять пользовательские файлы.

Все конечные файлы, необходимые для публикации, должны находиться в `site/`. Не помещать публикуемые HTML, изображения и SEO-файлы за пределами этого каталога.

Временные исходные данные, скрипты миграции, логи и отчёты можно хранить в отдельном каталоге, например `migration/`, если они не нужны для публикации.

---

## 9. Этап 7. Публикация через GitHub Pages

Нужно не только подготовить статические файлы, но и настроить их публикацию.

Создать или аккуратно адаптировать workflow, например:

`.github/workflows/deploy-pages.yml`

Workflow должен:
1. Запускаться при push в основную ветку репозитория.
2. Поддерживать ручной запуск через `workflow_dispatch`.
3. Устанавливать зависимости и запускать генератор, если он используется.
4. Выполнять проверки собранного сайта.
5. Загружать как Pages artifact именно содержимое каталога `site/`.
6. Публиковать artifact через официальный механизм GitHub Pages Actions.

Предусмотреть необходимые permissions, в частности:
- `contents: read`;
- `pages: write`;
- `id-token: write`.

Использовать актуальные совместимые официальные GitHub Actions для конфигурации Pages, загрузки артефакта и деплоя.

Проверить настройки репозитория:

`Settings → Pages → Build and deployment → Source → GitHub Actions`.

Не публиковать корень репозитория вместо `site/`.

Если в репозитории уже есть GitHub Pages workflow, другой сайт или процесс деплоя, сначала изучить конфигурацию и не ломать существующую публикацию. При необходимости согласовать новый workflow с уже существующими действиями.

Проверить наличие `CNAME` и уже настроенного пользовательского домена. Не менять DNS, не удалять `CNAME` и не переназначать домен без отдельного согласования.

Основная цель — получить работающий HTTPS-адрес GitHub Pages.

## 10. Этап 8. Автоматические и ручные проверки

Успешная генерация файлов или завершение GitHub Actions само по себе не доказывает, что перенос выполнен правильно.

### 10.1. Проверка полноты

Сопоставить реестр исходных материалов с итоговыми HTML-страницами.

Проверить:
- все найденные исходные материалы имеют соответствующие результаты;
- перенесены введение и заключение;
- не пропущены буквы и разделы, имеющиеся на источнике;
- каждая выставка имеет отдельный HTML-файл и URL;
- нет пустых страниц;
- нет случайных дублей;
- тексты не обрезаны;
- заголовки и порядок абзацев сохранены.

Автоматизировать сравнение там, где это возможно: например, нормализовать пробелы и HTML-сущности, извлечь текст из исходной и результирующей страницы и сравнить его. Различия из-за удаления навигации и шаблонной разметки допустимы, потери текста статьи — нет. Для неоднозначных случаев провести ручную проверку.

### 10.2. Проверка изображений

Пройти по всем HTML-страницам и проверить наличие каждого локального изображения.

Не должно быть:
- битых ссылок;
- ссылок на файлы вне `site/`;
- ссылок на несуществующие файлы;
- ошибок в регистре имён;
- случайно перепутанных изображений.

Сопоставить количество обнаруженных исходных иллюстраций с количеством перенесённых. Любое расхождение объяснить в отчёте.

### 10.3. Проверка ссылок

Проверить:
- ссылки на отдельные выставки;
- ссылки с алфавитных разделов;
- внутренние ссылки между статьями;
- ссылки на изображения;
- корректность относительных путей;
- работу ссылок при размещении в подпапке GitHub Pages.

### 10.4. Проверка HTML и SEO

Автоматически проверить:
- корректность HTML;
- наличие `title`, `description`, `h1` и canonical;
- уникальность title и URL;
- отсутствие пустых обязательных метаданных;
- корректность `sitemap.xml` и `robots.txt`;
- отсутствие случайного `noindex`;
- наличие основного текста непосредственно в HTML;
- отсутствие JavaScript-загрузки статей.

### 10.5. Проверка опубликованного сайта

После деплоя открыть именно опубликованный сайт и проверить:
- главную страницу;
- несколько алфавитных разделов, включая разделы в начале, середине и конце указателя;
- несколько отдельных выставок с разным количеством изображений;
- загрузку картинок;
- переходы между разделами и статьями;
- несуществующий URL и страницу `404.html`.

Проверять не только локальный preview, но и реальный адрес GitHub Pages.

## 11. Этап 9. Итоговый отчёт

После завершения работ подготовить отчёт, содержащий:

1. Сколько исходных страниц и разделов обнаружено.
2. Сколько отдельных описаний выставок найдено и перенесено.
3. Сколько материалов проверено полностью.
4. Сколько изображений найдено в репозитории.
5. Сколько изображений сопоставлено и использовано.
6. Какие изображения не удалось сопоставить или пришлось оставить без публикации.
7. Какие исходные материалы не удалось получить или перенести.
8. Какие каталоги, файлы и скрипты созданы.
9. Как устроено хранение материалов и генерация страниц.
10. Как организованы отдельные URL выставок и объединённые страницы разделов.
11. Какие SEO-файлы и метаданные добавлены.
12. Как настроен GitHub Pages workflow.
13. Результат последнего запуска GitHub Actions.
14. Адрес опубликованного сайта.
15. Результаты автоматических проверок и известные ограничения.

Не заявлять о стопроцентном переносе, если остались непроверенные, недоступные или отсутствующие материалы. Все проблемы перечислить явно.

---

## 12. Критерии завершения

Задача выполнена только при соблюдении всех применимых пунктов:

- [ ] Исходный сайт полностью инвентаризирован.
- [ ] Составлен реестр исходных материалов.
- [ ] Перенесены введение и заключение.
- [ ] Перенесены все доступные описания выставок.
- [ ] Каждое описание выставки представлено отдельным HTML-файлом и имеет собственный URL.
- [ ] Предусмотрены объединённые страницы разделов с несколькими выставками.
- [ ] Тексты перенесены без сокращений и пересказов.
- [ ] Изображения взяты из существующих файлов репозитория.
- [ ] Сопоставление изображений с материалами проверено.
- [ ] Сохранены порядок иллюстраций, их расположение и подписи.
- [ ] Все публикуемые файлы находятся в `site/`.
- [ ] Ссылки и ресурсы корректно работают на GitHub Pages.
- [ ] Созданы `sitemap.xml`, `robots.txt` и `404.html`.
- [ ] Настроен GitHub Actions для публикации именно содержимого `site/`.
- [ ] Workflow успешно выполнен.
- [ ] Опубликованный сайт доступен по HTTPS.
- [ ] Проверены реальные страницы и изображения на опубликованном сайте.
- [ ] Подготовлен итоговый отчёт с перечнем нерешённых проблем.

**Не останавливаться после создания структуры или переноса нескольких пробных статей. Выполнить полный перенос всех доступных материалов, настроить публикацию и проверить конечный результат. При обнаружении частичных ограничений продолжать работу над доступными материалами и подробно фиксировать оставшиеся проблемы.**
