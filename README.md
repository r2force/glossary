# Книга – Выставка – Читатель

Глоссарий нетрадиционных форм книжных выставок: [открыть сайт](https://glossary.ufacsdb.ru/).

Содержание и оформление хранятся в `site/`. Jekyll собирает полноценный статический HTML в `_site/`, который публикуется через GitHub Pages. Тексты доступны непосредственно в HTML.

## Окружение

Нужны Python 3.12 или новее, Ruby 3.3, Bundler, Node.js 20 или новее и Git LFS. Версии для разработки указаны в `.python-version` и `.ruby-version`. Все команды ниже выполняются из корня репозитория. Node.js используется для тестов поиска; npm-зависимости не требуются.

```bash
git lfs install
git lfs pull
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
BUNDLE_GEMFILE=site/Gemfile bundle install
```

Виртуальное окружение создаётся на текущей машине; не переносите `.venv` между ОС или версиями Python. Git LFS должен получить реальные изображения перед сборкой и проверкой.

Bundler должен соответствовать версии в конце `site/Gemfile.lock` (сейчас `2.5.22`): `gem install bundler -v 2.5.22`. На macOS системный Ruby 2.6 не подходит: используйте Ruby 3.3. Локальные настройки `PATH` и путей зависимостей можно сохранить в `.tools/env.sh`: `scripts/check.sh` автоматически подключает этот файл, если он существует. Каталог `.tools/` исключён из Git; CI использует окружение из workflow. Для отдельных команд сборки и просмотра сначала выполните `source .tools/env.sh`, если используете такое локальное окружение.

## Сборка и проверка

Полная локальная проверка:

```bash
PYTHON=.venv/bin/python scripts/check.sh
```

Без переменной `PYTHON` скрипт выбирает `.venv/bin/python`, если окружение создано, иначе `python3`. По отдельности:

```bash
.venv/bin/python -m unittest discover -s tests
node --test tests/*.test.cjs
BUNDLE_GEMFILE=site/Gemfile bundle exec jekyll build --source site --destination _site --strict_front_matter
.venv/bin/python scripts/verify_media.py --site _site
.venv/bin/python scripts/verify_site.py --site _site --repeat
```

Проверки сопоставляют исходники Jekyll с готовым HTML, проверяют локальные ссылки, изображения, метаданные, sitemap, префикс проекта и повторяемость сборки. Они проверяют текущее содержание репозитория; правильность редакторских изменений оценивается при просмотре diff и затронутых страниц.

Поиск доступен в шапке каждой страницы и по `Ctrl/⌘ + K`. Он ищет по полному тексту всех выставок, введения и заключения; при вводе показывает заголовки и фрагменты с выделением совпадений. Несколько слов должны встречаться в одной статье; регистр и различие `е`/`ё` не учитываются. При переходе из результата совпадения выделяются и в самой статье. Индекс `site/assets/search.json` создаётся Jekyll из исходников автоматически.

Для локального просмотра из корня сайта, как на собственном домене:

```bash
BUNDLE_GEMFILE=site/Gemfile bundle exec jekyll serve --source site --destination _site
```

Откройте [локальный сайт](http://127.0.0.1:4000/).

## Где менять сайт

| Задача | Файлы |
| --- | --- |
| Изменить или добавить выставку | `site/_exhibitions/<slug>.html` |
| Изменить буквенный раздел | `site/_sections/<letter>.html` |
| Изменить введение или заключение | `site/index.html`, `site/conclusion/index.html` |
| Изменить меню или алфавит | `site/_data/navigation.yml`, `site/_data/alphabet.yml` |
| Изменить общий HTML и оформление | `site/_layouts/`, `site/_includes/`, `site/assets/site.css` |
| Изменить адрес и настройки Jekyll | `site/_config.yml` |
| Изменить официальную электронную почту во всех контактных ссылках | `official_email` в `site/_config.yml` |
| Изменить проверки и CI | `scripts/`, `tests/`, `.github/workflows/` |

Официальная почта задаётся только в `official_email` в `site/_config.yml`. Контактные кнопки помечаются `data-email` без адреса: общий шаблон передаёт его в обратном порядке, а JavaScript раскрывает обычную почтовую ссылку по нажатию. Открытый адрес не попадает в HTML и поисковый индекс; это затрудняет простой сбор адресов, но не останавливает ботов, исполняющих JavaScript.

Новая выставка — отдельный HTML-файл с YAML front matter и полным текстом:

```html
---
title: "Название выставки"
letter: "А"
order: 1000
---
<p>Полный текст материала.</p>
```

Выберите свободное имя файла и значение `order`, задающее место в списке. Значение `letter` должно соответствовать существующему разделу. Для новой буквы добавьте файл в `_sections/`; полный алфавит хранится в `_data/alphabet.yml`. Шаблоны автоматически включают выставки в соответствующий раздел, поиск и sitemap. На главной странице размещено введение с кнопкой перехода к указателю.

Имя файла выставки определяет постоянный адрес `/exhibitions/<slug>/`, имя файла раздела — `/sections/<letter>/`. Сохраняйте существующие имена при изменении заголовков. Если нужен новый URL, предусмотрите сохранение переходов со старого адреса.

В статьях хранится только содержание: общий `<html>`, `<head>`, меню и основной `<h1>` создают шаблоны. Сохраняйте авторские повторы, структуру, подписи и порядок иллюстраций, если задача не предусматривает редактуру. Изображения добавляйте в `site/images/`, проверяйте регистр пути, содержательный `alt` и Git LFS по `.gitattributes`.

Ссылки внутри сайта и изображения формируйте через `relative_url`, который учитывает `baseurl` (для действующего домена он пустой):

```html
<a href="{{ '/exhibitions/akrostih/' | relative_url }}">Выставка – акростих</a>
<img src="{{ '/images/stories/exhibition/horovod/horovod1.jpg' | relative_url }}" alt="Иллюстрация выставки «Хоровод»">
```

## Публикация

Постоянное требование пользователя для агента: после задачи с изменениями выполнить проверки, создать коммит и всегда отправить готовые изменения в `origin/main` без дополнительного подтверждения. Push запускает публикацию; агент дожидается workflow и проверяет сайт. Правило закреплено в `AGENTS.md`; явная просьба не отправлять изменения в конкретной задаче имеет приоритет.

`.github/workflows/build-check.yml` проверяет pull request в `main`. После push в `main` workflow `.github/workflows/deploy-pages.yml` собирает сайт, выполняет проверки, загружает только `_site/` как Pages artifact и проверяет опубликованные HTTPS-адреса. Workflow также поддерживает ручной запуск.

В настройках репозитория источник GitHub Pages — GitHub Actions, пользовательский домен — `glossary.ufacsdb.ru`. В `site/_config.yml` заданы `url: "https://glossary.ufacsdb.ru"` и пустой `baseurl`: сайт работает из корня домена. Проверка в workflow использует адрес, возвращённый GitHub Pages при публикации, с принудительным HTTPS. `_site/` не коммитится.

## Поисковая оптимизация и аналитика

На всех страницах установлен счётчик Яндекс Метрики **110935159** из `yandex_metrika_id` в `site/_config.yml`. Подключение асинхронное, с картой кликов, точным показателем отказов, отслеживанием ссылок и резервным noscript-пикселем. Параметры соответствуют предоставленному коду; Вебвизор не включён. Код хранится в `_includes/yandex-metrika.html`.

Общий `head.html` формирует уникальные title и description, canonical, Open Graph и Twitter Cards. Для страницы можно задать `seo_title`, `description`, `image`, `image_alt`; видимый авторский заголовок при этом сохраняется. У статей описание выводится из авторского текста, у буквенных разделов — из состава раздела. `_plugins/seo_filters.rb` очищает описание, ограничивает его длину и выбирает оригинал иллюстрации вместо миниатюры. Если иллюстрации нет, используется фотография из `social_image`. Даты публикации и изменения не выдумываются.

`structured-data.html` формирует WebSite, Article с организацией-составителем, CollectionPage с реальным списком статей и BreadcrumbList по видимой навигации. Sitemap содержит все доступные для индексации страницы и оригиналы изображений; 404 имеет `noindex, follow` и не входит в sitemap. Поиск остаётся доступным через HTML-ссылки, а страницы результатов в виде отдельных индексируемых URL не создаются. Проверки сверяют метаданные, JSON-LD, состав каталогов, хлебные крошки, изображения и единственное подключение Метрики.

После публикации владельцу сайта нужно:

1. Проверить посещения в кабинете Метрики и исключить собственные визиты, если это требуется для отчётов. Код на сайте не подтверждает права доступа к кабинету и не доказывает поступление данных в отчёты.
2. Добавить `https://glossary.ufacsdb.ru/` в [Яндекс Вебмастер](https://yandex.ru/support/webmaster/ru/service/rights) и [Google Search Console](https://support.google.com/webmasters/answer/9008080), если сайт ещё не подключён. Для подтверждения через метатег достаточно сохранить выданные сервисами значения в `yandex_verification` и `google_site_verification` в `_config.yml`; значения нельзя подменять номером счётчика.
3. Отправить `https://glossary.ufacsdb.ru/sitemap.xml` в разделе Sitemap обоих сервисов и проверить индексацию нескольких статей. [Инструкция Яндекса](https://yandex.ru/support/webmaster/ru/indexing-options/sitemap), [инструкция Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).
4. После накопления данных смотреть поисковые запросы, показы, переходы и вовлечённость. По этим данным выбирать статьи для содержательного дополнения примерами, анонсировать материалы на сайте ЦСДБ и в профессиональных библиотечных сообществах.

Изменения улучшают техническую доступность и описание материалов; позиции, выбор сниппета и сроки переиндексации определяет поисковая система. Подключение кабинетов и подтверждение владения требуют учётной записи владельца и не выполняются одной установкой Метрики.
